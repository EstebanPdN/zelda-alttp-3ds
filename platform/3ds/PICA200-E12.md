# E12: implemented Old 3DS PICA200 PPU

E11 reduced CPU background work; it did not move the SNES PPU to the GPU.
E12 introduces a separate backend enabled by default on Old 3DS after startup
checks. This is an implementation, not the E11 GPU design proposal. New 3DS
continues using its previous renderer, CPU/core policy and UI texture format.

## Frame ownership and rendering

`ZeldaTryGpuPpu` captures the existing SimpleHdma/IRQ register sequence for all
224/240 visible lines. A separate PPU snapshot retains VRAM, OAM and CGRAM.
Successful frames skip both `PpuBeginDrawing`'s retained software preparation
and every CPU `ppu_runLine`; the CPU builds tile/sprite geometry instead.

`ppu_gpu_model.c` keeps an 8192-slot, 1024x512 RGBA8 tiled atlas. Tile identity
includes VRAM address, bit depth and palette; source bytes and colors validate
cached entries once per frame. Direct memory changes between frames are seen.
Only changed slots are decoded and cache-cleaned. Slots referenced by current
geometry cannot be evicted, and pending dirty slots survive a rejected frame.

Background geometry observes the existing window spans, tilemap quadrants,
scroll offsets, flips, priorities and extended-camera bounds. Sprite row
fragments reproduce OAM order and scanline sprite/sliver limits. Stencil claims
the first opaque sprite even if its depth fails behind a background: a later
sprite with higher BG priority cannot leak through it.

PICA renders main/sub layers into RGBA8 textures with depth/stencil, then a
six-stage TEV program resolves SNES clipping, math eligibility, fixed color,
subscreen backdrop exceptions, add/subtract and halving into RGBA5551. The
encoded source component `8*n+1` preserves 5-bit quantization through TEV's
integer operations, including half-add's 128/255 interpolation coefficient.
The presenter samples this GPU result directly with identity channel mapping.

The previous GPU frame completes before retained vertex/atlas storage is
modified. Clears, draws and transfers remain in Citro3D command order. There
is no per-gameplay-frame allocation. Pixel positions, depth, UV and color fit
in 16-byte vertices; PICA performs coordinate conversion. Adjacent scanline
states are compared once to prepare bands reused by every drawing pass. Main/sub textures and depth buffers plus
the resolve texture consume about 2.25 MiB VRAM; atlas, vertex arena and
readback reserve about 6.5 MiB linear RAM (plus ordinary CPU metadata).

## Startup verification and fallbacks

Every Old 3DS launch checks 65,536 color combinations and an 89,600-pixel,
400x224 synthetic scene against the established CPU renderer. The latter
exercises real shader coordinates, atlas sampling, depth/stencil, windows and
composition. Neither test uses ROM assets. A mismatch disables GPU drawing for
that session and reports the first expected/actual pixel; failing probe images
are retained for the next dump. Startup probes do not count as gameplay frames.

The first implementation accepts Mode 1 at full brightness without active
mosaic. Mode 7, brightness fades, mosaic, live mid-frame VRAM/CGRAM/OAM writes,
capacity errors and requested CPU thumbnails/performance overlays use the
existing CPU renderer for that frame. Register-only HDMA is supported. Failed
preflight restores the PPU snapshot before CPU replay; it never displays a
partial GPU frame. The next compatible frame can use PICA again. Fatal GPU
submission/init/probe errors explicitly disable the session.

`PICA frames_attempted/submitted/cpu_frames` and the 120-frame backend history
in `ppu.txt` distinguish actual gameplay submission from a probe or a fallback.
`frame-times.csv` still records the complete frame timings. GPU history records
preparation, prior GPU wait, geometry build, submission, uploaded tile bytes,
vertices, decodes and fallback reason. On a CPU row those are GPU preflight
costs, not CPU PPU execution time. Prior GPU wait includes driver/GPU retirement;
submit time is command submission, not GPU execution duration.

`pica-source.raw` is a 512x256 resolved GPU image as little-endian u32 00RRGGBB;
its active viewport is described in `ppu.txt`. Physical display captures still
include scaling, margins and overlays. CPU priority buffers are stale on a GPU
frame and must not be interpreted as that frame's rendered scene. Numbering
remains `000-dump-YYYYMMDD-HHMMSS`, `001-dump-...` and so on.

## Citro2D handoff and library compatibility

After the GPU pass all TEV/buffer, alpha, stencil and scissor state is restored.
`C2D_Prepare` itself enables depth: the color-only display depth policy is
restored **after** that call. Enabling depth with no display depth allocation
is invalid and was caught during emulator validation.

Citro3D 1.7.1's public `C3D_TexBind(1, NULL)` dereferences the null texture while
checking its type. Leaving the second sampler enabled is also invalid with
Citro2D's shader, which supplies no UV1. The narrow `ppu_gpu_c3d.h` adapter uses
the unmodified v1.7.1 internal declaration to unbind that unit and mark it dirty.
A pointer-layout canary rejects an incompatible dependency before GPU setup.
No library function is replaced and New 3DS never calls this adapter. The
vendored declaration and upstream license are preserved with the source.

## Validation and limits

- Host ASan/UBSan rasterization of emitted geometry: 4096 randomized scenes,
  cold/warm atlas, all sprite sizes/limits, windows, math, native/wide output,
  direct memory changes and 224/240-row boundaries; four user dump states.
- Independent SNES arithmetic reference: all 65,536 color combinations.
- Azahar 2126.0 software PICA backend: both actual startup probes pass exactly.
  Vulkan/Metal quantizes RGB5 render targets differently and the exact color
  probe rejects it; use the software backend for this correctness test.
- Existing CPU fallback, New 3DS reference, presentation, bottom-menu and audio
  shutdown tests remain part of the release validation.

Host instruction counts or emulator frame rates are not physical Old 3DS FPS.
The user's latest E11 dumps show about 26.8–27.1 FPS outdoors and 33.2–35.6 in
interiors, with CPU PPU wall time 25.9–35.6 ms. E12 removes that CPU rasterization
on supported frames, but its total CPU preparation/GPU/presentation cost and
60 FPS acceptance still require the physical console. No frame skipping,
resolution reduction or New 3DS performance profile change is used to claim it.
