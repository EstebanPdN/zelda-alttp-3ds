# E14: GPU dump readback and preparation overlap

## Supplied physical evidence

`000-dump-20260908-081938` is E12, with its known failed color probe.
The other two dumps are E13 on Old 3DS. GPU initialization and both startup
probes succeeded. Dump 001 submitted 2,102 GPU frames; dump 002 submitted 573.

The recent E13 samples average 35.02 visual FPS outside and 51.10 inside.
PPU wall spans are 26.82 / 17.94 ms. GPU preparation history averages:

| Phase | Exterior | Interior |
|---|---:|---:|
| Wait before CPU preparation | 7.12 ms | 6.18 ms |
| CPU geometry construction | 17.07 ms | 8.96 ms |
| GPU command submission | 0.41 ms | 0.32 ms |

These are wall spans including preemption, not pure CPU cycle measurements.
The samples demonstrate serialization of GPU retirement and CPU preparation.
Both E13 dumps stop after PPU priority blobs. Neither contains pica-source.raw,
bottom-ui.txt, runtime.log or manifest.txt. The next operation in the source
is PpuGpuReadback's transfer-only private Citro3D frame. This localizes the
stall to the GPU readback stage; the files do not establish whether the driver
stalls in frame/queue completion or the RGB5A1-to-RGBA8 conversion itself.

## Dump change

PpuGpuReadback no longer submits any GPU command or opens a private frame.
It waits at most one second for the current queue, then reads the existing
CPU-visible uncached VRAM result. It untwists the native 8x8 Morton layout
and expands RGB5 components to 00RRGGBB. Output format and numbered directory
names are unchanged. If waiting fails, it returns failure without touching
the image; the dump routine can finish its manifest and resume audio.

This removes the operation at which both physical dumps stopped. It does not
claim to recover from an unrelated GPU hang already present before capture.
The live CPU-read image was visually compared with the displayed image in
software PICA; host tests cover all 131,072 pixels and timeout propagation.

## Geometry change

PicaBuildFrame creates common bands only from visible Mode 1 register state.
SelectBands adds the particular background layer's map/scroll/tile inputs.
Other backgrounds, VRAM access latches and unused Mode 7 register changes no
longer split that pass into individual scanlines. HasLayer skips absent planes.

Objects first builds accepted per-line sliver masks with the original 32-OBJ/
34-sliver limits (or the user's existing no-limit option). A compact active
OAM list skips hidden entries. It then emits in original OAM order, merging
rows only within the same tile, flip direction, register/window band and
accepted-column mask. Transparent pixels still obey first-opaque-OAM stencil
ownership and background depth. All eight OBJ size modes are retained.

A first key-building approach increased CPU instructions and was rejected.
The final approach compares the common register range once, avoiding repeated
full-Ppu copies and repeated window-key construction.

Static ARMv6K replay (same inputs, warm caches, no GPU/OS/cache-miss timing):

| State | E13 preparation instructions | E14 | Reduction |
|---|---:|---:|---:|
| Exterior | 1,906,327 | 1,716,085 | 10.0% |
| Interior | 1,224,819 | 940,810 | 23.2% |

These are reconstructed static states, not live HDMA playback or measured FPS.
They do not include the benefit or cost of the overlapping resource buffers.

## CPU/GPU overlap and ownership

There are now two atlas/cache/vertex sets, allocated once at Old GPU startup.
SelectBuffers always chooses the opposite of lastSubmittedSlot, including
failed preflights. PpuGpuBegin can therefore prepare without waiting on the
GPU that is consuming the other set. Platform3DS_PresentTopFrame's existing
C3D_FrameBegin still retires the previous queue before submitting another.
At most one frame uses GPU resources concurrently with CPU preparation.

Each atlas has its own source/palette validation, eviction state and dirty
ranges. There is no whole-atlas copy each frame. GPU startup probes and
shutdown retain actual completion fences. New 3DS does not allocate or use
these resources. Two sets cost approximately 6 MiB more linear memory and
one extra cache in normal heap; allocation failure retains the CPU fallback.
Schema 3 reports the current/submitted slots and CPU dump method. Waiting
left at presentation is measured by frame-times.csv gpu_begin_us; old
prior_gpu_wait_us is now zero because preparation no longer waits there.

## Validation and scope

- 2,048 randomized CPU-vs-GPU geometry scenes plus both new E13 dump states,
  with ASan/UBSan: exact pixels, cold/warm atlases, all OBJ sizes, windows,
  priorities, half/add/subtract, native/wide and changing per-line registers.
- 65,536 independent color cases and actual TEV regression tests.
- Actual buffer selection/Begin in 1,000 GPU/CPU fallback cycles with retry
  attempts: no writes to the simulated in-flight resource set.
- Actual CPU capture routine: complete Morton layout/RGB expansion and timeout.
- Existing Old/New menu rendering, runtime-setting persistence, New E6 parity,
  Citro2D state handoff and ordered audio shutdown regressions.
- Actual cross-built Old binary: zero color/geometry probe mismatches and
  consecutive complete GPU dumps while frame submissions continue advancing.

Physical E14 dump recovery, images, memory headroom under real scenes and
sustained 60 FPS still require an Old 3DS run. Emulator rates and instruction
counts are never represented as hardware performance. All output remains local.
